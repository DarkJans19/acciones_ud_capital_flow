# Requirements Document

## Introduction

This spec covers the backend for development modules MOD-01 (Identity, Security and Access Control) and MOD-02 (Market Explorer and Stock Quotes) of the AccionesUD Capital Flow platform. The backend is a REST API built with Python and FastAPI, integrated with Alpaca (Broker API and Market Data API, sandbox environment) and persisting data in Supabase (Postgres). The frontend is built by another team and consumes the OpenAPI contract generated by FastAPI.

Every requirement keeps its original project ID (RF-xx for functional requirements, RFP-xx for proposed requirements) for traceability. All RF and RFP items assigned to MOD-01 and MOD-02 are in scope.

RFP-01 (KYC, Requirement 10) and RFP-08 (interests and dashboard, Requirement 11) are in scope by explicit decision of the user, which overrides the "pending approval" status recorded for them in specs/01-identity-security.

Requirements 20 to 25, and the changes to Requirements 2, 4, 6 and 17 recorded in decisions D5 to D11, close the backend gaps listed in `readme_agregar.md` (gap IDs A1, A2, A3, B3, B4, C1, D1 and D3). Gaps B1, B2 and D2 of that document are out of scope (see Out of scope).

### Alignment with the team's specs/ folder

- This spec (.kiro/specs/identity-market-backend) is the single documentation base chosen by the team for MOD-01 and MOD-02. specs/01-identity-security and specs/02-market-data are superseded by this spec and are not a source of requirements for this work.
- This spec keeps these rules taken from the superseded specs: MFA recovery codes (Requirement 18), no self-assignment of privileged roles (Requirement 2), price freshness and delayed-data indicators (Requirement 13), and market depth limited to what the provider supplies (Requirement 19).
- CSRF and Origin validation from the superseded specs is deliberately left out by team decision (D4). Cookies rely on the SameSite attribute only. CORS (Requirement 17 criterion 4) is kept.
- The error format is Error_Body. The application/problem+json format proposed in the superseded specs is not adopted.
- HTTP paths follow the Plan Maestro paths and are defined in the design document.

### Delivery constraints

- No approval gates from other people, no mandatory merges or PR reviews, and no CI gates are part of this work.
- The database schema is versioned with Alembic migrations in `migrations/versions/` (already configured in the repository). A developer applies them with `uv run alembic upgrade head` using `MIGRATION_DATABASE_URL`. Applying migrations is a manual developer step, not a CI gate or an approval step.

### Decisions

- **D1 (RF-02):** The second factor is TOTP (RFC 6238, authenticator app). Rationale: free, no external SMS or email provider, matches the project plan ("MFA/TOTP").
- **D2 (RF-01, RF-02):** Authentication is implemented inside the Backend_API (Argon2id password hashing, JWT in HTTP-only cookies), and Supabase is used only as the Postgres database. Rationale: Supabase Auth uses bcrypt, while the project plan specifies Argon2id and HTTP-only JWT cookies. The user confirmed this decision: Supabase Auth is not adopted.
- **D3 (RF-03):** Access control is a simplified RBAC: three roles (investor, broker, administrator), permission codes attached to roles, and role assignments to users with validity periods.
- **D4 (RF-02, RFP-03):** The Backend_API implements no CSRF token and no Origin or Referer validation; cookie protection relies on the SameSite attribute of the Access_Token and Refresh_Token cookies (Requirement 3 criterion 3). Rationale: university project, decided by the team; CSRF and Origin validation can be added later if the frontend team asks for it. CORS restricted to configured origins (Requirement 17 criterion 4) is kept, because the frontend calls the API from another origin.
- **D5 (RFP-02, RFP-01, gap A3 of readme_agregar.md):** Broker activation also grants the investor role. The activation request creates, in the same transaction, a broker Role_Assignment and an investor Role_Assignment (Requirement 2 criteria 12 and 14), so an activated Broker holds `kyc:submit` through the investor role and can open the Alpaca account. The RBAC seed of the Migration_Set is not changed: `kyc:submit` stays attached to the investor role only. Rationale: user decision (option b of gap A3).
- **D6 (RFP-02, gap D1):** The broker request flag stored at investor registration becomes queryable (Requirement 22). The investor is still created active with the investor role; the flag grants nothing by itself. Rationale: user decision (option a of gap D1).
- **D7 (RF-03, RFP-01, gaps A1 and A2):** Administrators get a user directory (list and detail) that includes the locally stored KYC data (Requirements 20 and 21). No separate administrative KYC endpoint is added and the directory never calls the Alpaca_Broker_API. Rationale: user decision (simple option of gap A2).
- **D8 (RFP-01, RF-06, gap B3):** The Alpaca account status is kept current by a periodic KYC_Refresh_Job, and the account information endpoint reuses a recently confirmed stored status instead of calling the Alpaca_Broker_API on every request (Requirement 23). The degraded fallback of Requirement 6 criterion 5 is kept. Rationale: user decision.
- **D9 (RFP-01, gap B4):** A KYC submission that ends in the "KYC completion requires reconciliation" state is repaired through an administrative, idempotent reconciliation endpoint (Requirement 24). Rationale: user decision.
- **D10 (RFP-03, gap C1):** Logout always succeeds with HTTP 204 and always clears both auth cookies; when the Access_Token is not valid, the Refresh_Token cookie identifies the Session to revoke (Requirement 4 criteria 6, 11 and 12). Rationale: user decision; a 401 on logout adds no security and leaves the Session alive.
- **D11 (RF-03, gap D3):** Identity administrative actions are written to an Audit_Log in the same transaction as the action, and the Audit_Log is readable through an administrative endpoint guarded by the `admin:rbac` permission (Requirement 25). Rationale: user decision. The permission choice is explained in Requirement 25.

### Assumptions

- **A1:** Premium status is a flag on the user that an Administrator sets; payment (MOD-04) is out of scope.
- **A2:** The associated broker and the contracted plan (RF-06) are owned by MOD-06 and MOD-04; this backend returns them as nullable fields.
- **A3:** SMS sending is simulated (logged only). Email and Telegram sending go through a pluggable Notifier; in-app notifications are always stored in Supabase_DB.
- **A4:** Market data uses the Alpaca free plan IEX feed by default; the feed is a configuration value.
- **A5:** Sector and market capitalization are not provided by Alpaca; the optional sector field of an Instrument is maintained in Supabase_DB by the Migration_Set seed data or by an Administrator.
- **A6:** Order controls (RF-09) and portfolio view settings (RF-08) are stored by this backend and enforced or applied by MOD-03 and MOD-05.
- **A7:** Default token lifetimes are 15 minutes for the Access_Token and 7 days for the Refresh_Token, both configurable.
- **A8:** Broker accounts created through RFP-02 start with the Account_Status pending_broker_activation and hold no broker permissions until an Administrator activates them through the Backend_API (Requirement 2). Broker activation is an in-product administrator action of the running system; it is not an approval gate on development work.
- **A9:** For US equities, the Alpaca_Market_Data_API provides only top of book (best bid and best ask with their sizes) on the iex, sip and delayed_sip feeds, and no full order book depth. This assumption must be verified against the contracted Alpaca plan; if the plan provides more price levels, Requirement 19 criterion 2 must be revised.
- **A10 (gap D1):** An Administrator promotes an investor whose broker request flag is true through the existing role assignment endpoint (Requirement 5 criterion 2, `POST /api/v1/admin/users/{user_id}/roles` with role `broker`). The code allows this only for a requester holding `admin:rbac` and an Effective_Role of administrator (`routers/admin.py`, `create_assignment`). The broker activation endpoint stays limited to Users with the Account_Status pending_broker_activation (Requirement 2 criterion 13). Promotion does not change the broker request flag; the flag records what the User asked for at registration. The user has not decided whether promotion should clear the flag.
- **A11 (gap C1):** At logout, a Refresh_Token that is expired or previously rotated still identifies its Session for revocation. This matches Requirement 4 criterion 2, where presenting such a token already revokes the Session.
- **A12 (gap B3):** The account information endpoint may store the KYC status it retrieves from the Alpaca_Broker_API (Requirement 23 criterion 5). This is the only stored data that endpoint changes, and it is needed so that the cache of Requirement 23 also works when the KYC_Refresh_Job is disabled.
- **A13 (gap B4):** The Alpaca_Broker_API account list endpoint (`GET /v1/accounts` with the `query` parameter) matches a token against the account number, phone number, name or email address of each account ([Alpaca docs](https://docs.alpaca.markets/eu/reference/getallaccounts)). Reconciliation without an explicit Alpaca account identifier searches by the User's registered email. Because the query also matches account numbers, phone numbers and names, the backend keeps only the returned accounts whose contact email equals the registered email (Requirement 24 criterion 2). The KYC contact email submitted under Requirement 10 is not stored locally and can differ from the registered email; in that case the search finds no account or more than one, and the Administrator supplies the Alpaca account identifier (Requirement 24 criteria 1, 3 and 4).
- **A14 (gap C1):** "Logout always returns 204" covers every credential state (valid, expired, missing). When Supabase_DB is unavailable the Session cannot be revoked, so logout returns HTTP 503 DATABASE_UNAVAILABLE while still clearing both cookies (Requirement 4 criterion 14). A 204 in that case would report a closed Session that is still alive. To be confirmed by the user.

### Out of scope

Orders (MOD-03), wallet, funding and Stripe premium payments (MOD-04), portfolio (MOD-05), broker network (MOD-06), administration parametrization screens (MOD-07), mobile (MOD-08), and the frontend.

Audit (MOD-07) is out of scope except for the Audit_Log of identity administrative actions (Requirement 25, gap D3). Audit of orders, portfolios, funds or any other module stays out of scope.

These gaps of `readme_agregar.md` are out of scope by user decision, because AGENTS.md requires an approved spec for the portfolio and broker modules before they are implemented:

- **B1 (balances and positions endpoint):** belongs to the portfolio module (MOD-05), which has no approved spec.
- **B2 (financial fields of the Alpaca account: cash, buying power, portfolio value, equity):** only needed by the portfolio endpoint of B1, so it follows the same portfolio spec.
- **D2 (contracted plan and associated broker in account information):** needs the broker–client relation of the broker module (MOD-06) and the plans of MOD-04; Requirement 6 criterion 2 keeps returning both fields as null.

## Glossary

- **Backend_API**: The FastAPI application that exposes the REST and WebSocket endpoints described in this spec.
- **Auth_Service**: Component of the Backend_API that handles registration, password login, TOTP verification and token issuance.
- **Session_Service**: Component of the Backend_API that manages sessions, devices, token refresh and logout.
- **RBAC_Service**: Component of the Backend_API that manages roles, permissions, role assignments and authorization checks.
- **Account_Service**: Component of the Backend_API that returns account information and stores user preferences.
- **KYC_Service**: Component of the Backend_API that collects identity data and opens and tracks the Alpaca brokerage account.
- **Dashboard_Service**: Component of the Backend_API that builds the initial dashboard from user interests and level.
- **Market_Service**: Component of the Backend_API that serves asset catalog, exchanges, quotes, bars, calendar and clock data.
- **Watchlist_Service**: Component of the Backend_API that manages watchlists and price alerts.
- **Alert_Engine**: Background process of the Backend_API that evaluates active price alerts and market open and close events.
- **Notifier**: Pluggable component that stores in-app notifications and dispatches them to external channels (email, SMS, Telegram).
- **Alpaca_Broker_API**: Alpaca Broker API (sandbox) used for accounts, assets, calendar and clock.
- **Alpaca_Market_Data_API**: Alpaca Market Data API used for latest quotes, trades, snapshots and historical bars.
- **Supabase_DB**: The Supabase Postgres database used for persistence.
- **Migration_Set**: The Alembic revisions in migrations/versions/ that create the tables, constraints and seed data in Supabase_DB.
- **User**: Any registered account, regardless of role.
- **Investor**: User holding the investor role.
- **Broker**: User holding the broker role (comisionista).
- **Administrator**: User holding the administrator role.
- **Premium_User**: User whose premium flag is true.
- **Access_Token**: Short-lived JWT carried in an HTTP-only cookie that authenticates API requests.
- **Refresh_Token**: Long-lived opaque or JWT token carried in an HTTP-only cookie that obtains a new Access_Token.
- **MFA_Challenge**: Short-lived token (5 minutes) issued after a correct password, required to submit the TOTP code.
- **TOTP_Code**: Six-digit time-based one-time password (RFC 6238, 30-second step).
- **Session**: Server-side record of one authenticated login, linked to one Refresh_Token and one device description (user agent and IP address).
- **Role_Assignment**: Record linking a User to a role with a valid_from timestamp and an optional valid_to timestamp.
- **Effective_Role**: A role whose Role_Assignment satisfies valid_from <= current time and (valid_to is null or current time < valid_to).
- **Instrument**: Asset record from the Alpaca asset catalog, cached in Supabase_DB, with optional sector data.
- **Market**: An exchange or trading venue (for example NYSE, NASDAQ) with its schedule configuration.
- **Schedule_Override**: Administrator-defined record that sets the open time, close time, or closed status of a Market for a specific date.
- **Watchlist**: Named list of Instruments owned by one User.
- **Price_Alert**: Rule owned by a Premium_User with an Instrument, a comparator (above, below, crosses) and a numeric threshold.
- **Notification**: Stored message with recipient, type, payload, channel, and creation timestamp.
- **Error_Body**: JSON response body with the fields code (string), message (string) and details (object or null).
- **Account_Status**: Status of a User account, exactly one of active or pending_broker_activation.
- **Recovery_Code**: Single-use code of exactly 10 characters drawn from uppercase letters A to Z and digits 0 to 9, issued in sets of 10 per User, that can replace one TOTP_Code in MFA verification.
- **Staleness_Threshold**: Configurable number of seconds, an integer from 1 to 86,400 with a default of 900, above which a price is reported as stale.
- **Depth_Level**: One price level of the order book with bid price, bid size, ask price and ask size.
- **User_Directory_Service**: Component of the Backend_API that lists and returns Users for Administrators, including their locally stored KYC data.
- **KYC_Refresh_Job**: Background process of the Backend_API, owned by the identity module, that periodically retrieves from the Alpaca_Broker_API the status of every linked KYC_Account.
- **Audit_Log**: Append-only store in Supabase_DB of Audit_Entries for identity administrative actions.
- **Audit_Entry**: One Audit_Log record with an identifier, the actor User identifier, an action code, a target type (user or role), a target identifier, a payload object and an occurred_at timestamp.
- **KYC_Account**: The record in Supabase_DB that links one User to an Alpaca account: Alpaca account identifier (nullable), stored status, status update timestamp, Status_Check_Time, reservation timestamp, last four characters of the tax identifier (nullable) and creation timestamp.
- **KYC_Link_State**: State of a User's KYC_Account, exactly one of: none (no KYC_Account exists), unlinked (a KYC_Account exists without an Alpaca account identifier) or linked (a KYC_Account exists with an Alpaca account identifier).
- **Status_Check_Time**: Timestamp of the latest successful retrieval of a KYC_Account status from the Alpaca_Broker_API, whether or not the status changed.
- **Broker_Request_Flag**: The boolean broker request flag stored with a User at registration (Requirement 1 criterion 2), false when the registration request omits it.

## Requirements

### Requirement 1: Register investor (RF-01)

**User Story:** As a prospective investor, I want to register with my personal data and password, so that I can access the platform.

#### Acceptance Criteria

1. WHEN a registration request contains every required field (first names, last names, email, phone, country of residence, password, terms acceptance set to true, and the monthly report option as a boolean) and every supplied field passes validation, THE Auth_Service SHALL create exactly one User with the investor role, ignore any role value supplied in the request, and return HTTP 201 with a body containing the User identifier.
2. WHEN a valid registration request is processed, THE Auth_Service SHALL store with the User the supplied optional fields: interests (0 to 20 entries, each 1 to 50 characters), investor level (exactly "beginner" or "experienced"), broker request flag (boolean) and premium request flag (boolean). For each optional field the request omits, THE Auth_Service SHALL store an empty interests list, no investor level, or false, according to the field.
3. THE Auth_Service SHALL store the password only as an Argon2id hash and SHALL never persist the plaintext password.
4. IF the terms acceptance field is false, missing, or not a boolean, THEN THE Auth_Service SHALL reject the registration with HTTP 422 and an Error_Body, and SHALL create no User.
5. IF every field passes validation and the email, after removing leading and trailing whitespace, matches the email of an existing User in a case-insensitive comparison, THEN THE Auth_Service SHALL reject the registration with HTTP 409 and an Error_Body, and SHALL neither create a User nor modify the existing User.
6. IF any required field is missing, or any of these checks fails, THEN THE Auth_Service SHALL reject the registration with HTTP 422 and an Error_Body naming each missing or invalid field, and SHALL create no User:
   - first names or last names are empty after trimming, or longer than 100 characters;
   - the email format is invalid, or the email is longer than 254 characters;
   - the phone is not in E.164 format;
   - the country is not an ISO 3166-1 alpha-2 code;
   - the password has fewer than 8 or more than 128 characters, or lacks at least one letter or at least one digit;
   - the monthly report option, broker request flag or premium request flag is not a boolean;
   - the investor level is not "beginner" or "experienced";
   - interests fall outside the bounds in criterion 2.
7. THE Auth_Service SHALL exclude the password and the password hash from every API response, including success responses and every Error_Body.
8. IF two or more registration requests whose emails match in a case-insensitive comparison are processed at the same time, THEN THE Auth_Service SHALL create exactly one User, return HTTP 201 for that request, and return HTTP 409 with an Error_Body for every other request.
9. IF the Auth_Service cannot persist the User because the database is unavailable or the write fails, THEN THE Auth_Service SHALL return HTTP 503 with an Error_Body code DATABASE_UNAVAILABLE indicating that registration could not be completed, and SHALL leave no User or partial User data stored.

### Requirement 2: Role-differentiated registration (RFP-02)

**User Story:** As a platform operator, I want broker and administrator accounts with role-specific data, so that each role has the information it needs.

#### Acceptance Criteria

1. WHEN a broker registration request contains the registration fields of Requirement 1 criterion 1 plus a firm name of 1 to 200 characters and a professional license number of 1 to 50 characters (both lengths measured after trimming leading and trailing whitespace), THE Auth_Service SHALL create a User with the Account_Status pending_broker_activation and no Role_Assignment, store the firm name and professional license number with the User, and return HTTP 201 with the User identifier and the Account_Status.
2. WHEN a request carrying a valid, unexpired Access_Token of a User with an Effective_Role of administrator submits an administrator account creation request containing the registration fields of Requirement 1 criterion 1, THE Auth_Service SHALL create a User whose only Role_Assignment is the administrator role with valid_from set to the creation time and valid_to null, and return HTTP 201 with the User identifier.
3. IF a request carrying a valid, unexpired Access_Token of a User without an Effective_Role of administrator submits an administrator account creation request or a broker activation request, THEN THE Backend_API SHALL reject the request with HTTP 403 and an Error_Body, create no User and no Role_Assignment, and leave the Account_Status of every User unchanged.
4. IF a broker registration request lacks the firm name or the professional license number, or either value is empty after trimming or exceeds its maximum length from criterion 1, THEN THE Auth_Service SHALL reject the request with HTTP 422 and an Error_Body naming each missing or invalid field, and create no User.
5. THE Migration_Set SHALL create exactly one initial Administrator from values read from environment variables at migration time: INITIAL_ADMIN_EMAIL, INITIAL_ADMIN_PASSWORD_HASH (a precomputed Argon2id hash), INITIAL_ADMIN_FIRST_NAMES, INITIAL_ADMIN_LAST_NAMES, INITIAL_ADMIN_PHONE and INITIAL_ADMIN_COUNTRY. THE Migration_Set SHALL also give that Administrator an administrator Role_Assignment with valid_from set to the migration execution time and valid_to null.
6. THE Auth_Service SHALL apply Requirement 1 criteria 3 through 9 (Argon2id password storage, terms acceptance, case-insensitive duplicate email, field format validation, password exclusion from responses, concurrent duplicate email handling, and database unavailability) to broker registration requests and administrator account creation requests, with the same HTTP status codes and Error_Body responses, and SHALL store no Role_Assignment for a request those criteria reject.
7. IF an administrator account creation request or a broker activation request has no valid, unexpired Access_Token, THEN THE Backend_API SHALL reject the request with HTTP 401 and an Error_Body, create no User and no Role_Assignment, and leave the Account_Status of every User unchanged.
8. IF the Migration_Set runs while a User already exists with the INITIAL_ADMIN_EMAIL email (case-insensitive comparison), THEN THE Migration_Set SHALL leave that User and its Role_Assignments unchanged and create no additional Administrator.
9. THE Auth_Service SHALL set the Account_Status active for every User created through Requirement 1 criterion 1 or through criterion 2 of this requirement.
10. THE Migration_Set SHALL set the Account_Status active for the initial Administrator created by criterion 5.
11. WHILE a User has the Account_Status pending_broker_activation, THE RBAC_Service SHALL evaluate that User as holding no Effective_Role, so that every endpoint requiring a permission code returns HTTP 403 with an Error_Body as described in Requirement 5 criterion 9.
12. WHEN a request carrying a valid, unexpired Access_Token of a User with an Effective_Role of administrator requests the broker activation of an existing User whose Account_Status is pending_broker_activation, THE RBAC_Service SHALL, in one atomic operation, create a broker Role_Assignment and an investor Role_Assignment for that User, each with valid_from set to the request time and valid_to null, set the Account_Status to active, and return HTTP 200 with the User identifier, the Account_Status, the created broker Role_Assignment and the created investor Role_Assignment (decision D5). The activated Broker then holds every permission of the broker role and of the investor role, including kyc:submit through the investor role, and the role permissions stored by the Migration_Set stay unchanged.
13. IF a broker activation request references an existing User whose Account_Status is not pending_broker_activation, THEN THE RBAC_Service SHALL return HTTP 409 with an Error_Body code BROKER_NOT_PENDING, create no Role_Assignment, and leave the Account_Status unchanged.
14. IF two or more broker activation requests for the same User are processed at the same time, THEN THE RBAC_Service SHALL let exactly one of them succeed as described in criterion 12, SHALL handle every other request as described in criterion 13, and SHALL leave that User with exactly one broker Role_Assignment and exactly one investor Role_Assignment created by the activation.
15. THE Backend_API SHALL create broker and administrator Role_Assignments only from requests carrying a valid, unexpired Access_Token of a User with an Effective_Role of administrator, or through the Migration_Set under criterion 5, so that a public registration request (investor or broker) creates no broker or administrator Role_Assignment regardless of any role value the request supplies.
16. IF any write of the broker activation of criterion 12 fails, THEN THE RBAC_Service SHALL return HTTP 503 with an Error_Body code DATABASE_UNAVAILABLE, and SHALL leave the Account_Status pending_broker_activation with neither the broker Role_Assignment nor the investor Role_Assignment of that activation stored.
17. IF a broker activation request from a User with an Effective_Role of administrator references a User identifier that matches no existing User, THEN THE RBAC_Service SHALL return HTTP 404 with an Error_Body, and create no Role_Assignment.
18. IF, when the Migration_Set runs, any of the environment variables of criterion 5 is missing or empty, or INITIAL_ADMIN_EMAIL, INITIAL_ADMIN_FIRST_NAMES, INITIAL_ADMIN_LAST_NAMES, INITIAL_ADMIN_PHONE or INITIAL_ADMIN_COUNTRY fails the format check of Requirement 1 criterion 6 for its field, or INITIAL_ADMIN_PASSWORD_HASH does not start with the Argon2id prefix `$argon2id$`, THEN THE Migration_Set SHALL stop with an error naming each missing or invalid variable, whether or not a User with the INITIAL_ADMIN_EMAIL email already exists, and SHALL create no User and no Role_Assignment.

### Requirement 3: Authenticate with MFA (RF-02)

**User Story:** As a User, I want to log in with email, password and a TOTP code, so that my account is protected by a second factor.

#### Acceptance Criteria

1. WHEN a login request contains a registered email (compared case-insensitively after trimming leading and trailing whitespace) and the matching password, THE Auth_Service SHALL return HTTP 200 with a newly issued MFA_Challenge that expires 300 seconds after issuance, and SHALL NOT set any Access_Token or Refresh_Token cookie or include either token in the response body.
2. WHILE the User has no confirmed TOTP enrollment, WHEN the User submits a correct password, THE Auth_Service SHALL include a TOTP secret and an otpauth provisioning URI (6 digits, 30-second period) in the login response. IF the User already has a confirmed TOTP enrollment, THEN THE Auth_Service SHALL NOT include the TOTP secret or provisioning URI in any response.
3. WHEN an unexpired, unused MFA_Challenge and a valid TOTP_Code are submitted, THE Auth_Service SHALL confirm the TOTP enrollment if it is pending, create a Session in Supabase_DB, set the Access_Token (expiring 15 minutes after issuance) and the Refresh_Token (expiring 7 days after issuance) as cookies with the HttpOnly and Secure attributes and a SameSite attribute of Lax or Strict, mark the MFA_Challenge as used, and return HTTP 200 with the authentication result.
4. THE Auth_Service SHALL accept a TOTP_Code of exactly 6 digits that matches the current 30-second step or the step immediately before or after it, and SHALL reject a TOTP_Code that matches only steps outside this window.
5. IF the email is unknown or the password does not match, THEN THE Auth_Service SHALL return HTTP 401 with an identical Error_Body code for both cases, and SHALL issue no MFA_Challenge.
6. IF the TOTP_Code does not match the accepted step window, OR the TOTP_Code's step is equal to or earlier than the step of the User's last accepted TOTP_Code, OR the MFA_Challenge is expired, already used, or unknown, THEN THE Auth_Service SHALL return HTTP 401 with an Error_Body, issue no tokens, create no Session, and leave a pending TOTP enrollment unconfirmed.
7. WHEN a login or TOTP verification attempt completes, THE Auth_Service SHALL record in Supabase_DB the User identifier (when the email matches a registered User), the UTC timestamp, the IP address, the user agent (truncated to 512 characters), and the result as either success or one failure reason from: unknown email, wrong password, invalid TOTP_Code, replayed TOTP_Code, expired MFA_Challenge, invalid MFA_Challenge, or attempt limit exceeded. The record SHALL NOT contain the submitted password, the TOTP_Code, or the TOTP secret.
8. WHEN an authenticated request is sent to the current user endpoint, THE Auth_Service SHALL return HTTP 200 with the User identifier, names, email, Effective_Roles and premium flag, and SHALL NOT return the password hash or the TOTP secret.
9. IF a protected endpoint receives a request with no Access_Token cookie, or with an Access_Token whose signature is invalid, whose expiry time has passed, or whose Session has been revoked, THEN THE Backend_API SHALL return HTTP 401 with an Error_Body and SHALL NOT execute the requested operation.
10. IF 5 TOTP verification attempts against the same MFA_Challenge fail, THEN THE Auth_Service SHALL invalidate that MFA_Challenge, so that any later submission with it, including one with a valid TOTP_Code, returns HTTP 401 with an Error_Body and issues no tokens.
11. IF a login request has an email that is missing, longer than 254 characters, or not in email address format, or a password that is empty or longer than 128 characters, or a TOTP verification request has a TOTP_Code that is not exactly 6 digits, THEN THE Auth_Service SHALL return HTTP 422 with an Error_Body identifying the invalid field, without checking credentials or using up a failed attempt on the MFA_Challenge.
12. IF Supabase_DB is unavailable while a login or TOTP verification request is being processed, THEN THE Auth_Service SHALL return HTTP 503 with an Error_Body, issue no MFA_Challenge or tokens, and create no Session.

### Requirement 4: Manage sessions, devices and logout (RFP-03)

**User Story:** As a User, I want to see and close my active sessions, so that I can control which devices access my account.

#### Acceptance Criteria

1. WHEN a request is sent to the refresh endpoint with a Refresh_Token cookie that is unexpired, unrevoked, not previously rotated, and linked to an active Session, THE Session_Service SHALL issue a new Access_Token that expires at most 15 minutes after issuance, issue a new Refresh_Token that expires at most 7 days after issuance, set both tokens as HTTP-only cookies (the Access_Token cookie on path / and the Refresh_Token cookie on path /api/v1/auth), invalidate the previous Refresh_Token, and set the Session last-used timestamp to the time of the request. An active Session is one that has not been revoked and whose latest Refresh_Token has not expired.
2. IF a refresh request presents a Refresh_Token that is expired, revoked, previously rotated, or linked to a revoked Session, THEN THE Session_Service SHALL return HTTP 401 with an Error_Body, revoke the Session linked to that Refresh_Token (a Session that is already revoked stays revoked), issue no new Access_Token or Refresh_Token, and clear the Access_Token and Refresh_Token cookies as described in criterion 13.
3. WHEN an authenticated User requests the session list, THE Session_Service SHALL return every active Session of that User, and only that User's active Sessions, sorted by last-used timestamp from newest to oldest. Each entry SHALL contain the Session identifier, user agent, IP address, creation timestamp, last-used timestamp, and a flag that is true for the entry of the Session making the request and false for every other entry.
4. WHEN an authenticated User requests closing one of the User's own active Sessions, THE Session_Service SHALL revoke that Session, leave every other Session of that User unchanged, return a success response, and reject that Session's Refresh_Token on every later refresh request as described in criterion 2.
5. WHEN an authenticated User requests closing all other Sessions, THE Session_Service SHALL revoke every active Session of that User except the current Session, keep the current Session active with its Refresh_Token valid, leave the Sessions of every other User unchanged, and return a success response that includes the number of Sessions revoked. The number is 0 when no other active Session exists.
6. WHEN a logout request carries a valid, unexpired Access_Token linked to an unrevoked Session, THE Session_Service SHALL revoke that Session and only that Session, clear the Access_Token and Refresh_Token cookies, and return HTTP 204 (decision D10). A Refresh_Token cookie in the same request SHALL NOT cause the revocation of any other Session. After logout, every refresh request that presents the Refresh_Token of that Session SHALL be rejected as described in criterion 2.
7. IF an authenticated User requests closing a Session identifier that belongs to another User, does not exist, or refers to a Session that is already revoked, THEN THE Session_Service SHALL return HTTP 404 with an Error_Body, use the same Error_Body code for all three cases, and leave every Session unchanged. A Session identifier that is not a valid UUID is rejected with HTTP 422 as in Requirement 17 criterion 2.
8. IF a refresh request has no Refresh_Token cookie or presents a Refresh_Token that cannot be parsed or verified, THEN THE Session_Service SHALL return HTTP 401 with an Error_Body, issue no new Access_Token or Refresh_Token, clear the Access_Token and Refresh_Token cookies as described in criterion 13, and leave every Session unchanged.
9. IF a request to the session list, close-session or close-all-other-sessions endpoint has no Access_Token cookie, or carries an Access_Token that is expired, cannot be parsed or verified, or is linked to a revoked Session, THEN THE Session_Service SHALL return HTTP 401 with an Error_Body, return no Session data, and leave every Session unchanged.
10. IF two or more refresh requests present the same valid Refresh_Token concurrently, meaning a second request arrives before the first has finished rotating that Refresh_Token, THEN THE Session_Service SHALL let at most one of them succeed as described in criterion 1, and SHALL handle every other request as using a previously rotated Refresh_Token as described in criterion 2.
11. IF a logout request has no Access_Token, or an Access_Token that is expired, invalid, or linked to a revoked Session, and carries a Refresh_Token cookie that matches a stored Refresh_Token (expired, previously rotated or current, Assumption A11), THEN THE Session_Service SHALL revoke the Session linked to that Refresh_Token when that Session is not yet revoked, leave every other Session unchanged, clear the Access_Token and Refresh_Token cookies, and return HTTP 204.
12. IF a logout request carries neither a valid Access_Token as described in criterion 6 nor a Refresh_Token cookie that matches a stored Refresh_Token as described in criterion 11, THEN THE Session_Service SHALL clear the Access_Token and Refresh_Token cookies, return HTTP 204, and leave every Session and every Refresh_Token unchanged.
13. WHEN the Session_Service clears the Access_Token and Refresh_Token cookies under criterion 2, 6, 8, 11, 12, 14 or 15, THE Session_Service SHALL include in that response a Set-Cookie header that expires the Access_Token cookie on path / and a Set-Cookie header that expires the Refresh_Token cookie on path /api/v1/auth, each with a maximum age of 0 or an expiry date in the past, so that the cookies are cleared whatever the Session outcome.
14. IF Supabase_DB is unavailable while a logout request is being processed, as defined in Requirement 17 criterion 9, THEN THE Session_Service SHALL return HTTP 503 with an Error_Body code DATABASE_UNAVAILABLE, leave every Session and every Refresh_Token as stored before the request, and still include the Set-Cookie headers of criterion 13 in that response.
15. WHEN the Session closed under criterion 4 is the current Session, THE Session_Service SHALL also clear the Access_Token and Refresh_Token cookies as described in criterion 13 in the success response.
16. IF Supabase_DB is unavailable while a refresh, session list, close-session or close-all-other-sessions request is being processed, as defined in Requirement 17 criterion 9, THEN THE Session_Service SHALL return HTTP 503 with an Error_Body code DATABASE_UNAVAILABLE, issue no new Access_Token or Refresh_Token, include no Set-Cookie header for either cookie, and leave every Session and every Refresh_Token as stored before the request.

5. WHEN an Administrator revokes an existing Role_Assignment, THE RBAC_Service SHALL set its valid_to to the time of the request, return HTTP 200 with the updated Role_Assignment, and exclude that Role_Assignment from the Effective_Roles used by every authorization check that starts after the response is returned.

WHEN an Administrator adds a permission code to a role or removes a permission code from a role, THE RBAC_Service SHALL store the change, return HTTP 200 with the role's resulting list of permission codes, and apply the change to every authorization check that starts after the response is returned.

10. IF a revoke or validity update request would leave zero Users holding an Effective_Role of administrator at the time of the request, THEN THE RBAC_Service SHALL reject the request with HTTP 409 and an Error_Body indicating that the last administrator cannot be removed, and SHALL leave the Role_Assignment unchanged.

12. IF an administration request references a User, role, Role_Assignment or permission code that does not exist, THEN THE RBAC_Service SHALL reject the request with HTTP 404 and an Error_Body identifying the missing resource, and SHALL leave all stored data unchanged.

5. WHEN a request carrying a valid, unexpired Access_Token of a User with the admin:rbac permission and an Effective_Role of administrator assigns the broker role through the role assignment endpoint of Requirement 5 criterion 2, THE RBAC_Service SHALL store the broker Role_Assignment and return the response defined in Requirement 5 criterion 2, whatever the value of the target User's Broker_Request_Flag. THE RBAC_Service SHALL also leave the target User's investor Role_Assignment, Account_Status and Broker_Request_Flag unchanged, so that later account information and User_Directory_Service responses for that User keep the same broker_requested value they returned before the assignment.
6. IF a request from a User holding the admin:rbac permission without an Effective_Role of administrator assigns the broker role to any User, THEN THE RBAC_Service SHALL return HTTP 403 with an Error_Body, store no Role_Assignment, and leave the target User's Account_Status and Broker_Request_Flag unchanged.
7. IF a broker activation request (Requirement 2 criterion 12) references a User whose Account_Status is active and whose Broker_Request_Flag is true, THEN THE RBAC_Service SHALL return HTTP 409 with an Error_Body code BROKER_NOT_PENDING as in Requirement 2 criterion 13, create no Role_Assignment, and leave that User's Account_Status and Broker_Request_Flag unchanged.
8. THE Backend_API SHALL set the Broker_Request_Flag only when it creates the User at registration. Any later request, including role assignment, role revocation, broker activation, preference updates and account information requests, SHALL leave the stored Broker_Request_Flag unchanged, even when that request body contains a broker_requested field.
9. IF an investor registration request supplies a broker request flag that is not a JSON boolean, THEN THE Auth_Service SHALL return HTTP 422 with an Error_Body code VALIDATION_ERROR naming the broker request flag field, as in Requirement 1 criterion 6, and create no User.

### Requirement 23: Alpaca account status refresh and cache (RFP-01, RF-06)

**User Story:** As a User, I want my trading readiness to stay current without the profile depending on Alpaca on every request, so that my profile loads even when Alpaca is slow.

Source: `readme_agregar.md` gap B3 (P2). Decision D8, Assumption A12. The KYC_Refresh_Job belongs to the identity module and follows the background job pattern of `market_data/adapters/inbound/jobs/`.

#### Acceptance Criteria

1. THE Backend_API SHALL read three configuration values from environment variables at startup: KYC_STATUS_REFRESH_ENABLED (true or false, compared case-insensitively, default false), KYC_STATUS_REFRESH_INTERVAL_SECONDS (integer from 60 to 86,400, default 900) and KYC_STATUS_CACHE_TTL_SECONDS (integer from 0 to 3,600, default 60). Each variable that is not set SHALL take its default value.
2. WHERE KYC_STATUS_REFRESH_ENABLED is true, THE KYC_Refresh_Job SHALL start its first cycle KYC_STATUS_REFRESH_INTERVAL_SECONDS after the Backend_API finishes starting. In each cycle it SHALL retrieve from the Alpaca_Broker_API the status of every KYC_Account whose KYC_Link_State is linked at the start of the cycle, with a 10-second timeout per status request.
3. WHERE KYC_STATUS_REFRESH_ENABLED is false, THE Backend_API SHALL start no KYC_Refresh_Job and SHALL send no KYC_Account status request to the Alpaca_Broker_API outside the handling of an API request.
4. WHEN an authenticated User with a linked KYC_Account requests account information, THE Account_Service SHALL return the stored KYC status without calling the Alpaca_Broker_API if the Status_Check_Time is not null and is no more than KYC_STATUS_CACHE_TTL_SECONDS before the request time. In every other case it SHALL retrieve the status from the Alpaca_Broker_API with a 10-second timeout. A failure of that retrieval SHALL be handled as in Requirement 6 criterion 5.
5. WHEN the KYC_Refresh_Job, the KYC_Service (Requirement 10 criterion 4) or the Account_Service (criterion 4) successfully retrieves the status of a linked KYC_Account from the Alpaca_Broker_API, THE Backend_API SHALL set the Status_Check_Time of that KYC_Account to the retrieval time. It SHALL store the retrieved status and update the status update timestamp only when the retrieved status differs from the stored status, as in Requirement 10 criterion 4. If the stored Status_Check_Time is already later than that retrieval time, the Backend_API SHALL instead leave the stored status, status update timestamp and Status_Check_Time unchanged. A retrieval that fails or times out SHALL change none of the three values.
6. WHERE KYC_STATUS_CACHE_TTL_SECONDS is 0, THE Account_Service SHALL retrieve the KYC status from the Alpaca_Broker_API on every account information request of a User with a linked KYC_Account.
7. IF the Alpaca_Broker_API returns an error other than HTTP 429, or does not respond within 10 seconds, for one KYC_Account during a KYC_Refresh_Job cycle, THEN THE KYC_Refresh_Job SHALL leave the stored status, status update timestamp and Status_Check_Time of that KYC_Account unchanged and SHALL continue with the remaining KYC_Accounts of the cycle.
8. IF the Alpaca_Broker_API returns HTTP 429 during a KYC_Refresh_Job cycle, THEN THE KYC_Refresh_Job SHALL end that cycle, send no further status request in it, keep the KYC_Account updates already stored in that cycle, leave every KYC_Account not yet refreshed unchanged, and start the next cycle as in criterion 14.
9. IF Supabase_DB becomes unavailable or an unexpected error occurs during a KYC_Refresh_Job cycle, THEN THE KYC_Refresh_Job SHALL end that cycle and send no further status request in it. It SHALL keep the KYC_Account updates already stored in that cycle and leave every other KYC_Account unchanged. It SHALL record the failure in the application log without any credential value or tax identifier, and SHALL keep running so that the next cycle starts as in criterion 14.
10. WHEN the KYC_Refresh_Job stores a retrieved status, THE KYC_Refresh_Job SHALL update only the KYC_Account whose stored Alpaca account identifier equals the identifier of the retrieved account. It SHALL create no KYC_Account and change no Alpaca account identifier.
11. IF the Account_Service retrieves the KYC status while serving an account information request, and storing the retrieved values fails because Supabase_DB is unavailable or the write does not complete, THEN THE Account_Service SHALL still return HTTP 200 with the retrieved KYC status and every other field of Requirement 6 criterion 1, and SHALL NOT set kyc_status_unavailable to true. The stored status, status update timestamp and Status_Check_Time of that KYC_Account SHALL keep their previous values.
12. IF KYC_STATUS_REFRESH_ENABLED is set, including to an empty string, to a value other than true or false (compared case-insensitively), or if KYC_STATUS_REFRESH_INTERVAL_SECONDS or KYC_STATUS_CACHE_TTL_SECONDS is set, including to an empty string, to a value that is not an integer within its bounds of criterion 1, THEN THE Backend_API SHALL refuse to start and SHALL send no request to the Alpaca_Broker_API. It SHALL report the name of every invalid variable in the startup error without reporting any variable's value.
13. WHEN the Backend_API shuts down, THE Backend_API SHALL send no new KYC_Refresh_Job status request after shutdown begins. It SHALL stop the KYC_Refresh_Job, waiting at most 10 seconds for an in-flight status request to finish, before it closes the Alpaca_Broker_API client. Updates already stored SHALL be kept, and a status request still in flight when the wait ends SHALL change no KYC_Account.
14. WHERE KYC_STATUS_REFRESH_ENABLED is true, THE KYC_Refresh_Job SHALL run at most one cycle at a time. It SHALL start each later cycle KYC_STATUS_REFRESH_INTERVAL_SECONDS after the previous cycle ends, whether that cycle completed, ended under criterion 8 or ended under criterion 9.

### Requirement 24: KYC reconciliation (RFP-01)

**User Story:** As an Administrator, I want to repair a KYC submission that Alpaca accepted but the backend failed to record, so that the User's Alpaca account is linked without manual database edits.

Source: `readme_agregar.md` gap B4 (P2). Decision D9, Assumption A13. In the current code, `KycService.submit` returns HTTP 503 with the message "KYC completion requires reconciliation." when the Alpaca account was created but the KYC_Account completion write matched no reservation; the KYC_Account then stays unlinked or, after a later released reservation, does not exist.

#### Acceptance Criteria

1. WHEN a request carrying a valid, unexpired Access_Token of a User whose Effective_Roles grant the admin:users permission is sent to `POST /api/v1/admin/kyc/{user_id}/reconcile` with a body whose alpaca_account_id is a valid UUID, for an existing User whose KYC_Link_State is none, or is unlinked with a reservation timestamp at least 120 seconds before the request time, THE KYC_Service SHALL retrieve that account from the Alpaca_Broker_API. When the account exists and its identifier is stored in no other User's KYC_Account, THE KYC_Service SHALL store in that User's KYC_Account the Alpaca account identifier, the status returned by the Alpaca_Broker_API, a status update timestamp equal to the time of the retrieval, and a Status_Check_Time equal to the time of the retrieval. It SHALL create the KYC_Account, with a null last four characters of the tax identifier, when the KYC_Link_State is none. It SHALL then return HTTP 200 with user_id, alpaca_account_id, status and outcome set to linked.
2. WHEN a reconciliation request whose body is absent, is an empty object, or holds a null alpaca_account_id is sent for an existing User whose KYC_Link_State meets the conditions of criterion 1, THE KYC_Service SHALL query the Alpaca_Broker_API account list with the User's registered email as the query value (Assumption A13). It SHALL keep only the returned accounts whose contact email equals the registered email in a case-insensitive comparison. When exactly one account remains and its identifier is stored in no other User's KYC_Account, it SHALL link that account as in criterion 1.
3. IF no account remains after the email filter of criterion 2, or the Alpaca_Broker_API reports that the alpaca_account_id of criterion 1 does not exist, THEN THE KYC_Service SHALL return HTTP 404 with an Error_Body code KYC_RECONCILE_NOT_FOUND, leave the KYC_Account unchanged, and store no Audit_Entry.
4. IF more than one account remains after the email filter of criterion 2, THEN THE KYC_Service SHALL return HTTP 409 with an Error_Body code KYC_RECONCILE_AMBIGUOUS whose details hold the number of remaining accounts as an integer and whose message asks for an alpaca_account_id, and SHALL leave the KYC_Account unchanged.
5. WHEN a reconciliation request is sent for a User whose KYC_Link_State is linked, and the request either omits alpaca_account_id (absent body, empty object or null value) or supplies an alpaca_account_id equal to the stored Alpaca account identifier when compared as UUID values, THE KYC_Service SHALL return HTTP 200 with user_id, the stored alpaca_account_id, the stored status and outcome set to already_linked. It SHALL send no request to the Alpaca_Broker_API and leave the KYC_Account unchanged.
6. IF a reconciliation request supplies an alpaca_account_id that differs, compared as UUID values, from the stored Alpaca account identifier of a User whose KYC_Link_State is linked, THEN THE KYC_Service SHALL return HTTP 409 with an Error_Body code KYC_ACCOUNT_EXISTS, send no request to the Alpaca_Broker_API, and leave the KYC_Account unchanged.
7. IF the account to link under criterion 1 or 2 is already stored as the Alpaca account identifier of another User's KYC_Account, THEN THE KYC_Service SHALL return HTTP 409 with an Error_Body code ALPACA_ACCOUNT_IN_USE, leave every KYC_Account unchanged, and store no Audit_Entry.
8. IF the User's KYC_Link_State is unlinked and the stored reservation timestamp is less than 120 seconds before the request time, THEN THE KYC_Service SHALL return HTTP 409 with an Error_Body code KYC_SUBMISSION_IN_PROGRESS, send no request to the Alpaca_Broker_API, and leave the KYC_Account unchanged.
9. IF, during a reconciliation request, the Alpaca_Broker_API fails under the conditions of Requirement 17 criterion 5 or 6, or the Supabase_DB fails under the conditions of Requirement 17 criterion 9 (including while storing the KYC_Account after a successful retrieval), THEN THE KYC_Service SHALL return the HTTP status and Error_Body code that the matching criterion defines, leave the KYC_Account unchanged, and store no Audit_Entry.
10. THE KYC_Service SHALL keep the stored last four characters of the tax identifier unchanged when it reconciles an existing KYC_Account. It SHALL store no other part of a tax identifier. It SHALL exclude every tax identifier value from the reconciliation response, from every Error_Body and from every log entry.
11. FOR ALL reconciliation requests that return outcome linked, repeating the same request SHALL return HTTP 200 with the same user_id and alpaca_account_id and with outcome already_linked, and SHALL leave the KYC_Account unchanged (idempotence).
12. IF two or more reconciliation requests for the same User, or a reconciliation request and a KYC submission (Requirement 10) for the same User, are processed at the same time, THEN THE KYC_Service SHALL keep at most one KYC_Account for that User. It SHALL store at most one Alpaca account identifier for that User and never overwrite an identifier that is already stored. It SHALL return outcome linked for at most one reconciliation request, and SHALL handle every other reconciliation request as described in criterion 5, 6, 7 or 8.
13. IF a reconciliation request references a user_id that is a valid UUID and matches no User, THEN THE KYC_Service SHALL return HTTP 404 with an Error_Body code NOT_FOUND and send no request to the Alpaca_Broker_API. IF the user_id is not a valid UUID, or the body alpaca_account_id is present, not null and not a valid UUID, THEN THE Backend_API SHALL return HTTP 422 with an Error_Body code VALIDATION_ERROR naming the invalid field and send no request to the Alpaca_Broker_API.
14. IF a reconciliation request has no valid, unexpired Access_Token, THEN THE Backend_API SHALL return HTTP 401 with an Error_Body. IF the requesting User lacks the admin:users permission through every Effective_Role, THEN THE Backend_API SHALL return HTTP 403 with an Error_Body as in Requirement 5 criterion 9. In both cases the KYC_Account stays unchanged, no Audit_Entry is stored, and no request is sent to the Alpaca_Broker_API.

### Requirement 25: Audit log of identity administrative actions (RF-03)

**User Story:** As an Administrator, I want a record of who changed roles, permissions, premium status, broker activations and KYC links, so that every administrative change can be traced.

Source: `readme_agregar.md` gap D3 (P2). Decision D11. This requirement narrows the MOD-07 audit exclusion of the Introduction to identity administrative actions only.

The read endpoint is guarded by admin:rbac rather than admin:users. Rationale: the Audit_Log records permission and role changes, which are governed by admin:rbac; a User who may only manage user accounts (admin:users) should not read the history of access-control changes. Both permissions are attached only to the administrator role by the Migration_Set, so the choice changes nothing for the current Administrators.

#### Acceptance Criteria

1. WHEN one of these administrative requests returns a success response (HTTP 200 or HTTP 201), THE Backend_API SHALL store exactly one Audit_Entry for that request. The entry holds the action code shown, the User identified by the request's Access_Token as actor, the target shown, and the payload keys shown. Each payload value equals the value stored by that request. The entry is stored even when the stored value equals the value held before the request:
   - administrator account creation (Requirement 2 criterion 2): action administrator_created, target the created User, payload with no keys;
   - broker activation (Requirement 2 criterion 12): action broker_activated, target the activated User, payload broker_assignment_id and investor_assignment_id;
   - premium flag change (Requirement 5 criterion 11): action premium_changed, target the User, payload is_premium holding the boolean value stored by the request;
   - Role_Assignment creation (Requirement 5 criterion 2): action role_assignment_created, target the User, payload assignment_id, role, valid_from and valid_to (null when no end is set);
   - Role_Assignment validity update (Requirement 5 criterion 4): action role_assignment_updated, target the User, payload assignment_id, role, previous_valid_from, previous_valid_to, valid_from and valid_to, where the previous_ values are those stored before the request;
   - Role_Assignment revocation (Requirement 5 criterion 5): action role_assignment_revoked when valid_to is set, or role_assignment_cancelled when a Role_Assignment that has not started yet is cancelled, target the User, payload assignment_id and role;
   - permission added to or removed from a role (Requirement 5 criterion 6): action role_permission_added or role_permission_removed, target the role, payload permission_code;
   - KYC reconciliation (Requirement 24 criteria 1, 2 and 5): action kyc_reconciled, target the User, payload alpaca_account_id and outcome, where outcome is linked for criteria 1 and 2 and already_linked for criterion 5.
2. THE Backend_API SHALL store each Audit_Entry with these fields: an identifier unique across the Audit_Log, the actor User identifier, the action code, the target type (user or role), the target identifier (User identifier or role code), the payload object of criterion 1, and an occurred_at UTC timestamp. The occurred_at value SHALL be no earlier than the time the Backend_API received the request and no later than the time it sent the response.
3. THE Backend_API SHALL store each Audit_Entry in the same database transaction as the administrative change it records, so that the change and its Audit_Entry are either both stored or both absent.
4. IF storing the Audit_Entry fails, THEN THE Backend_API SHALL return HTTP 503 with an Error_Body code DATABASE_UNAVAILABLE and leave the administrative change of that request unstored, with every value it would have changed equal to its value before the request.
5. IF an administrative request of criterion 1 returns an error response (any HTTP status of 400 or higher), THEN THE Backend_API SHALL store no Audit_Entry for that request.
6. THE Backend_API SHALL exclude from every Audit_Entry payload any password, password hash, TOTP secret, Recovery_Code, Access_Token, Refresh_Token, MFA_Challenge and any part of a tax identifier, including its last four characters.
7. WHEN a request carrying a valid, unexpired Access_Token of a User whose Effective_Roles grant the admin:rbac permission is sent to `GET /api/v1/admin/audit-log`, THE Backend_API SHALL return HTTP 200 with items, total, limit and offset. Items are Audit_Entries holding every field of criterion 2, ordered by occurred_at descending and, for equal occurred_at values, by identifier descending.
8. WHEN an audit log request supplies limit and offset, THE Backend_API SHALL accept limit as an integer from 1 to 100 (default 50) and offset as an integer of 0 or more (default 0). It SHALL return at most limit items, set total to the number of Audit_Entries that match every supplied filter regardless of limit and offset, and return an empty items list with that total when offset is equal to or greater than total.
9. WHEN an audit log request supplies one or more of the filters action (one action code of criterion 1), actor_user_id (UUID), target_type (user or role) and target_id (1 to 100 characters), THE Backend_API SHALL return only Audit_Entries whose field equals each supplied filter value, compared exactly and case-sensitively. When a well-formed filter value matches no Audit_Entry, THE Backend_API SHALL return HTTP 200 with an empty items list and total 0.
10. IF an audit log request has a filter value outside the values of criterion 9, or a limit or offset that is not an integer or is outside the bounds of criterion 8, THEN THE Backend_API SHALL return HTTP 422 with an Error_Body code VALIDATION_ERROR whose details name each invalid parameter, and SHALL return no Audit_Entry.
11. IF an audit log request has no valid, unexpired Access_Token, THEN THE Backend_API SHALL return HTTP 401 with an Error_Body and return no Audit_Entry.
12. THE Backend_API SHALL expose Audit_Entries only through the read endpoint of criterion 7, so that the OpenAPI document lists no endpoint that creates, updates or deletes an Audit_Entry.
13. IF an audit log request carries a valid, unexpired Access_Token of a User who lacks the admin:rbac permission through every Effective_Role, THEN THE Backend_API SHALL return HTTP 403 with an Error_Body as in Requirement 5 criterion 9, and return no Audit_Entry.
14. THE Backend_API SHALL leave every stored Audit_Entry unchanged after it is stored. No request, including the read endpoint of criterion 7 and every administrative request of criterion 1, modifies or deletes an existing Audit_Entry.
